# IBM Db2 for i as a primary database (phase 1). Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax; tick each one when it finishes, in the same work block.

**Goal:** `php artisan migrate:fresh --seed` and a Db2 test group pass on Db2 for i, through a fork of `easi-power/laravel-db2` that stays a generic driver, so that "Runs on IBM Db2 for i" can be claimed (phase 1 gate of the spec).

**Architecture:** Generic driver work lands in `swolley/laravel-db2`, one topic branch per gap, each ready to be offered upstream; an integration branch `laraplate` merges them and is what Laraplate requires. Laraplate names the Db2 driver family in one helper (`Db2Drivers`), gives every driver branch a Db2 arm or a documented exclusion, replaces generated columns with triggers on Db2, and gets a Db2 test run that only a dedicated invocation reaches.

**Tech Stack:** PHP 8.5, Laravel 13, Pest, `easi-power/laravel-db2` v14.4.0 forked, IBM i 7.5 on PUB400 through unixODBC, the IBM i Access ODBC driver and `pdo_odbc`.

**Spec:** `../specs/2026-11-17-db2-support-design.md` (approved by the user on 2026-11-26)

**Scope:** phase 1 only (Db2 for i). Phase 2 (LUW grammar with `SYSCAT` introspection, `truncate ... immediate`, LUW generated columns, the CI job on the Db2 Community Edition container, ODBC versus `pdo_ibm`) gets its own plan once the phase 1 gate holds, because its connection spike decides its shape.

## Global Constraints

- The fork stays a generic Laravel Db2 driver: no Laraplate names, tables or behaviour in it. Tests there use only the table names in the fork's `.claude/fixture-tables.txt` (`products`, `product_stock`, `orders`, `order_lines`, `customers`, `users`); a hook enforces it.
- Every fork topic branch starts from the fork's `master` (the upstream state) and carries its own unit tests on compiled SQL in `tests/Unit`. No upstream pull request is opened: whether and when is the user's decision.
- The fork's integration branch is `laraplate`: `master` plus a merge of each finished topic branch. Core requires `easi-power/laravel-db2: dev-laraplate`; the VCS entry goes in the root `composer.json` next to `swolley/license-compliance-checker`, with `"no-api": true`. Not Packagist.
- No IBM binary (ODBC driver, CLI driver) is committed anywhere.
- Registration follows the Oracle precedent: `easi-power/laravel-db2` in Core's `extra.laravel.dont-discover`, provider registered by `CoreServiceProvider` only when `pdo_odbc` is loaded and the class exists.
- A branch on the driver names the family through `Db2Drivers::family()` (Task 8), never the three driver names.
- Db2 for i has no expression-based generated columns: every derived column is a trigger on Db2.
- Full-text indexes, spatial columns and vector search are omitted on Db2, following the Oracle precedent, with the gap documented.
- Laraplate rules: `declare(strict_types=1)`, `vendor/bin/pint --dirty`, type coverage 100 % (`composer test:type-coverage`), never `mixed` to pass it, tests in the module's `tests/`, stubs only in `tests/Stubs/`, `vendor/bin/pest` (never `php artisan test`), no cached config.
- The default suite stays on SQLite. Every Db2 arm is proven in the default suite by tests on the SQL it builds (Task 8's pretend connection); the remote run is the gate, not the inner loop.
- A remote Db2 run sets `ALLOW_REMOTE_TEST_DATABASE=1` in its own invocation, never in a committed file.
- No public claim (README, website, docs) about Db2 before the gate is met and the user has chosen when to announce (spec, open decisions).
- Module work lands through a branch and a pull request per repository (Core, ERP, MES, Shop, root); the user merges. Commits carry no `Co-Authored-By` trailer.

## Review Focus

1. **A reserved-word column named in raw SQL.** `position`, `type`, `value`, `order` are created as `"POSITION"` and so on once quoting is on; a raw fragment that writes them bare still works only because Db2 folds bare names to upper case, but one written in lower case inside quotes breaks. Expected: raw SQL wraps column names through the grammar. Pinned in Task 5 (quoting of a wrapped reserved column inside `whereRaw`) and Task 13 (scan of raw SQL for reserved words).
2. **Multi-byte enum values.** `varchar(n)` on a UTF-8 (CCSID 1208) column counts bytes, so `città` needs 6, not 5. Pinned in Task 2.
3. **`insertOrIgnore` with a duplicate inside the same batch.** Two equal rows in one call: one stored, one ignored, the call returns 1. Pinned in Task 2.
4. **JSON paths with arrays and odd keys.** `meta->items[0]->sku` and a key with a dot must compile to a valid Db2 path. Pinned in Task 6.
5. **Tables that are not journaled.** On IBM i a rollback silently keeps the rows when the library is not journaled, so every test isolation and `DB::transaction` would lie. Expected: the run fails loudly. Pinned in Task 1 (spike) and Task 14 (a Db2 group test that rolls back and asserts the row is gone).
